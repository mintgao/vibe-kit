# Vibe Kit v0.11.0

Release candidate, unpublished when these notes were authored. These notes define
this version's exact scope; public completion and issue closure require their
separate observed evidence.

## Verification and maintenance changes

- `validate-publication --receipt` is exclusively read-only input. Optional
  `--result-receipt` creates one distinct outer result, refuses aliases, existing
  leaves and candidate descendants, and safely publishes without replacing a
  competing creation. Calls and nested validators cannot inherit result context.
- Equal transaction images satisfy both predecessor and target predicates.
  Repeated same-version upgrades retain the existing transaction, inode-pair,
  rollback and committed-recovery checks. A maintenance transaction reports its
  actual writes and never claims activation or readiness.
- `checks.log_policy: "all-configured"` or `verify --log-policy all-configured`
  opts into complete sanitized successful stdout/stderr. Default `failures`
  still selects failed/environment-limited output. Exact `stdout-stderr-v1`
  bytes have a private content-addressed path and SHA-256; final schema-2
  references keep the existing `output.full={path,sha256}` shape.
- `checks.progress: true` is the default, independently overridden by
  `--progress`/`--no-progress`. Private metadata-only execution schema 1 snapshots
  record before/after-check state, availability and final envelope digest without
  automatically persisting output bodies. The last-successfully-published
  locator is discovery-only. Completed JSON delivery contains one final result.
- Handled SIGINT/SIGTERM or runner errors produce honest incomplete/blocked
  evidence and preserve completed earlier checks. The direct shell is terminated
  and waited for within bounded limits; descendant termination remains
  `not-proven`. SIGKILL/crash can leave a running last observation with no result.
  A handled signal during terminal output stops delivery with exit 2 and binds
  incomplete progress/blocked-or-error explicit receipt when available. Escaped
  stdout can remain an unusable prefix; no replacement JSON, atomic delivery or
  downstream acknowledgement is promised.
- A bounded closed validator/safe reader checks metadata fields, combinations,
  canonical checksum, supplied result binding and requested actual artifacts.
  Progress never establishes acceptance or invalidates an otherwise independent
  complete valid receipt.
- Prospective applicable multi-stage M/L work can record approved outcome/AC
  references, stage scope/state, evidence, next action, role owner and waiting
  condition. Source Pass plus API Blocked plus export Unverified completes only
  the source stage. S, historical work, readiness, independent QA and host-only
  goal/custody boundaries remain intact. Static scenarios do not prove live-model
  compliance or measured efficiency.

## Privacy and compatibility

New directories are 0700, files 0600, with nested Git ignores and no-follow,
owner/single-link checks. Optional log/progress storage failures report
unavailable without changing project verdicts or stopping later independent
checks; explicit receipt write failure remains nonzero. Progress initialization/
publication resource exhaustion closes owned resources and makes that channel
unavailable while independent checks/logs/receipts continue. No automatic expiry,
quota deletion, raw-output spool, scheduler, telemetry or network operation is
added. Complete in-memory capture and opt-in disk retention can be substantial;
known-pattern sanitization is not universal secret detection. Keep logs private.

Receipt serialization is byte-identical for the same envelope values after
root-relative rewriting. Runtime outputs, observations and transaction identities
may differ; serialization does not make execution deterministic. Historical
receipts, logs and publication/closeout profiles retain their recorded meaning.
Old configurations are not rewritten. New config keys require a current parser;
older parsers continue rejecting unknown declarations.

Kit 0.11.0 retains core/Codex protocol 7, Hermes adapter protocol 1, Agent-install
schema/protocol 4/4, CLI result schema 2, takeover schema 2, maintenance bridge
schema 2, compatibility registry schema 2, release manifest schema 2,
transaction journal/commit schemas 1/1 and feedback protocol 2. The bridge's
exclusive upper bound and exact v0.5.0 predecessor migration target advance to
0.11.0 without changing predecessor eligibility or hashes. Python 3.9+ and
standard-library-only offline operation remain required.
