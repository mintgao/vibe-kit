## Post-upgrade automatic takeover

One exact project/version confirmation now governs trusted source resolution, a
read-only plan and safe apply without a redundant conversational confirmation.
The result then advances through separately evidenced upgraded, activated,
adapted, verified, re-evaluated and ready states.

The offline CLI proves filesystem and process facts only. The host-side Agent
adapter owns runtime activation, original-goal custody, project adaptation,
target-rule routing and the final ready message. Apply or doctor can never claim
activation or readiness.

## Current activation capability

Agent-install schema 2 defines same-task reload and automatic successor handoff,
but this repository and its bootstrap-only Plugin do not claim either without a
positive live host receipt. The portable behavior is one manual action: create a
new task in the same project. That task validates the actual target activation
identity, completes onboarding and default verification, re-evaluates the
preserved goal and resumes it when target rules permit.

Controlled fixtures validate the contract but do not count as live Codex host
conformance evidence.

`AGENT_INSTALL.md` and `agent-install.json` are installed, framework-managed and
activation-critical. Existing differing paths block preflight/upgrade, raw hashes
remain in the manifest, and doctor is broken if either installed contract is
missing, modified or structurally invalid.

Activation-set algorithm v2 avoids self-reference by hashing canonical
`agent-install.json` with only its activation digest replaced by 64 zeroes. The
CLI and an independent release reference path recompute the digest from actual
bytes.

Installed `validate-takeover --format json` authenticates the raw Agent-install
hash, core/manifest/activation identities and compiled registry digest before
checking the exact nested takeover structure. It persists and echoes no candidate
values. `valid` means structural consistency only and always reports
`host_evidence_authenticated=false` and `ready_claim=false`.

A clean current-project baseline combined the official 0.5.0 managed and
installation state with current project/application-owned files. The 0.6.0
target CLI produced a safe, read-only plan, authenticated the two official
predecessor contracts as one complete set, and scheduled their paired migration.
Apply and the target doctor then passed. The project/application-owned snapshot
remained byte-identical before and after upgrade (canonical SHA-256
`8136fa4f02166a3cb759f7f3b5b5f264349ae2392f5590f07cad225a013e96b1`),
and the worktree diff contained framework/tool-owned paths only.

The upgraded installation reported manifest SHA-256
`865048c76782083f5a75cc47b800095c9ad7190c9fa608a02adc5fb636b41a6e`,
matched activation set
`35f16a0c6393560794372737dc6a32b1d24a902e0f70d40989d9ce4e04d8a37c`,

was completed only across the documented manual-new-task boundary, with a

handoff. Python 3.9.25 passed the full 45-test suite, default verification,

available; live hot reload and automatic successor creation also remain
uncovered.

## Diagnostics and verification

JSON doctor receipts retain compatibility `warnings` and `errors` arrays and add
one authoritative closed diagnostic for each warning/error, including its fixed
readiness effect. Stale runtime paths block activation; stale non-runtime paths are
the only initial non-blocking warning class.

`verify --format json` emits a canonical lint/typecheck/test/build matrix. Empty
commands are unconfigured; every configured command is required for takeover.
Failures and provenance-bound skips block ready, while bounded redacted stdout and
stderr tails remain diagnostic evidence rather than takeover/goal-transfer data.

## Release boundary

This version is a GitHub Pre-release, not a stable promotion or public Plugin
Directory installation. It adds no network updater, task-creation API, reload API,
hook, MCP server or background process. Multi-file upgrade transactions and
rollback remain owned by the separate permission-safe atomic-upgrade work item.
